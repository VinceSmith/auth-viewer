About Entra OAuth Explorer

What is this?

Entra OAuth Explorer is an interactive teaching tool that visualizes OAuth 2.0 and Entra ID token flows in real time. It shows you exactly what happens at every step — the HTTP requests, the token exchanges, and the decoded JWT claims — so you can understand how authentication actually works.

How to Use

  1. Click ☰ to open the flow configuration menu
  2. Choose a grant type (User Auth or Client Credentials) and client type
  3. Pick a target resource from the dropdown
  4. Click Execute Flow (or Sign In & Execute for user flows)
  5. Step through results using the ◀ ▶ controls
  6. Explore each step's Summary, HTTP Request, HTTP Response, and Sign-in Log tabs
  7. Watch the sequence diagram on the left highlight the current step
  8. Click your profile avatar to inspect the ID token

Configuration

Flows are configured with three settings in the ☰ menu:

Grant Type

  • User Auth Flow (Delegated) — Uses the OAuth 2.0 Authorization Code grant. A user signs in via browser redirect and consents to scopes. The resulting token carries the user's identity (sub, upn) and delegated permissions (scp).
  • Client Credentials Flow — Uses the OAuth 2.0 Client Credentials grant. No user involved — the app authenticates as itself using a client secret. The resulting token carries application permissions (roles) and the app's identity.

Client Type

  • App (Service Principal) — A standard Entra ID application. The client app directly requests tokens from Entra ID using its own credentials.
  • Agent (Agent ID) — An Entra Agent Identity. The Blueprint app acquires a parent token, then the Agent Identity exchanges it for a downstream token via Workload Identity Federation. In delegated mode, the agent also performs an OBO exchange to preserve the user's context.

Target Resource

  • API A / API B / Graph — Direct token acquisition for a single resource.
  • API A → API B (OBO) — Multi-hop delegated chain. The client gets a user token for API A, then API A exchanges it for an API B token via On-Behalf-Of.
  • API A → Graph (OBO) — Same OBO pattern, targeting Microsoft Graph as the downstream resource.
  • API A → API B (chain) — Multi-hop app-only chain. The client gets an app token for API A, then API A does its own client credentials grant for API B.
  • API A → Graph (chain) — Same chain pattern, targeting Microsoft Graph downstream.

What You'll See

Each step exposes the full request/response lifecycle:

  • Summary — Key claims, parameters, and a plain-English explanation of what happened and why.
  • HTTP Request — The raw POST body sent to the token endpoint, including the access token used for API calls.
  • HTTP Response — The raw JSON response with decoded tokens inline. For authorize redirect steps, the full redirect URL with every query param is shown here.
  • Sign-in Log — The matching Entra ID sign-in log entry fetched from Microsoft Graph, so you can see exactly what Entra recorded for each token request.

The app also surfaces normally-hidden behaviors: scope coercion, token cache hits, audience mismatches, OIDC discovery, JWT validation steps, and consent pre-authorization — all annotated in the step descriptions.

Architecture

Three FastAPI services running together:

  • Client App — Main web app with UI, handles OAuth redirects and token exchanges
  • API A — Middle-tier API that validates tokens and performs OBO exchanges
  • API B — Downstream protected resource, the final target in OBO chains

App Registrations

Five Entra ID app registrations provide the identity infrastructure:

  • Client App — Confidential client that initiates all flows. Has delegated permissions to API A, API B, Graph, and the Blueprint.
  • API A — Exposes an access_as_user scope. Configured as an OBO client with permission to call API B on behalf of the user.
  • API B — Exposes a read scope. The downstream resource that only accepts tokens with its own audience.
  • Agent Blueprint — Defines the identity template for AI agents. Exposes an access_as_user scope and acts as the parent in agent token exchanges.
  • Agent Identity — A workload identity (service principal) created from the Blueprint. Uses Workload Identity Federation for token exchange without stored secrets.
